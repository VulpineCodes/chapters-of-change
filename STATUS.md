# Status: Chapters of Change

_Last updated: 2026-10-28 (final portfolio audit; see Verification below)_

## Done

- npm workspaces monorepo: `apps/api` (NestJS), `apps/web` (Next.js), `packages/domain` (pure TypeScript, zero runtime dependencies), `packages/app-services` (application and service layer, shipped as a built ESM package the API loads).
- Domain core: donation lifecycle state machine with `IllegalTransitionError` and audit history; listing model with search, filter, and pagination (`searchListings`); RBAC policy functions for `DONOR`, `ORG_ADMIN`, `ORG_MEMBER`, `ADMIN`; idempotency key helper plus an in-memory store modeling the database unique constraint contract; transactional outbox types plus an in-memory dispatcher with exponential backoff and an injectable sleeper. Design detail is in [ARCHITECTURE.md](./ARCHITECTURE.md).
- Application and service layer (`packages/app-services`): `WorkflowService` for the full donor to recipient workflow on top of the domain package; persistence behind repository interfaces (`Store`) with a verified in-memory adapter and a Prisma adapter written against `prisma/schema.prisma` (structurally typed client, `$transaction` as the atomicity boundary for status change plus outbox insert); notifications materialized from outbox events with retry, backoff, and `FAILED` visibility; `AuthService` issuing HS256 JWTs from stored user records.
- Nest services wired to the tested workflow. The `apps/api` listings and donations services and controllers delegate to `WorkflowService` through a shared singleton store from `RuntimeModule`. The HTTP surface: `POST /listings`, public search and get, `POST /donations` honoring the `Idempotency-Key` header, `GET /donations` with per-actor visibility, `GET /donations/:id`, and `POST /donations/:id/{approve,reject,cancel,in-transit,delivered,complete}`, all behind the existing `RolesGuard` and JWT handling. Workflow errors map to HTTP status codes: `AuthorizationError` to 403, `NotFound` to 404, validation to 400, `IllegalTransition` to 409, conflict to 409, invalid credentials to 401. The runtime store is selectable via `STORE_ADAPTER`: `memory` (default, verified, seeded) or `prisma` (selectable, fails fast without `DATABASE_URL`, labeled unverified).
- Credential login with bcrypt. `CredentialAuthService` in app-services: `POST /auth/register` hashes passwords with bcrypt (`bcryptjs`, cost 10) and stores only the hash; `POST /auth/login` verifies against the hash and issues the existing HS256 JWT. Unknown email and wrong password return the identical generic 401, and the unknown email path runs a dummy bcrypt comparison to blunt timing leaks. `POST /auth/dev-token` is kept but labeled DEV ONLY in code, Swagger, README, and `.env.example`. Seeded synthetic users have documented synthetic, dev only passwords there, bcrypt hashed at seed time in the in-memory path.
- Notification worker. The job processing core is a queue agnostic module (`NotificationWorkerCore`): it delivers a notification, retries with exponential backoff, and after max attempts moves the event to `FAILED` with the error preserved; `processPending` drains a store's outbox and persists final states. The BullMQ adapter (`apps/api/src/notifications/bullmq.adapter.ts`) wires that core to a real Queue and Worker and starts only when `REDIS_URL` is set. Without `REDIS_URL` the API boots with the worker disabled, a clear boot log line, and the state exposed in `GET /health`.
- JWT auth (`apps/api/src/auth/`): pure HS256 issuance and verification using Node's built-in `node:crypto` only. Algorithm pinned to HS256 (`none` rejected), `timingSafeEqual` signature comparison, `exp` required and enforced. `JwtService` is the Nest adapter, and `RolesGuard` builds `req.user` exclusively from verified Bearer token claims and distinguishes 401 (no valid token) from 403 (insufficient role). The Vitest suites test this exact module, not a copy.
- Prisma schema (`User`, `Profile`, `Organization`, `Listing`, `DonationRequest`, `Donation`, `OutboxEvent`, `Notification`; enums mirror domain) plus a hand-authored `0001_init` migration SQL consistent with the schema.
- Synthetic, clearly labeled seed data (`prisma/seed.ts`, mirrored in `packages/app-services/src/seed.ts` for orgs, users, and credentials; see the seed limitation below).
- Web: home, listings search (with loading, empty, and error states), donor dashboard, org dashboard, shared state components; Playwright config plus an E2E spec for the donor to recipient journey (`apps/web/e2e/`).
- Docker Compose (Postgres, Redis, API, Web), Dockerfiles, `.env.example`, and a GitHub Actions CI workflow file (`.github/workflows/ci.yml`) covering domain, app-services, API typecheck plus build plus HTTP smoke test, web build, and an E2E job that installs Playwright browsers. The workflow file exists in this local repo only; see the CI verdict below.

## Not verified / honest limitations

- No live Postgres or Redis, and no Docker, in this environment. Compose and Dockerfiles are authored but not run, and the Prisma adapter has not been executed against a real database. `STORE_ADAPTER=prisma` is wired and fails fast without `DATABASE_URL`, but it remains selectable and unverified. The verified persistence adapter is the in-memory one (state resets on restart). The workflow's transactional guarantees are proven against the in-memory transaction contract, with Prisma `$transaction` as the production boundary.
- BullMQ adapter has never run against a live Redis. Its delivery core (`NotificationWorkerCore`) is unit tested, and the API's no-Redis boot path is smoke tested. The adapter itself is typechecked and reviewed only, and is labeled unverified in code and docs.
- Docker Compose gap: Compose provisions Postgres and Redis and sets `DATABASE_URL` and `REDIS_URL` on the API service, but it does not set `STORE_ADAPTER`, so the API would still boot on the in-memory store. The Prisma path also needs a generated client and a migration run, which the API Dockerfile does not perform. Compose therefore does not yet deliver the database-backed stack it appears to describe.
- Dockerfiles use Node 22 as of this audit (bumped from Node 20 to match the `engines` requirement of Node 22 and the `require(esm)` loading path). That change has not been verified by a Docker build.
- Prisma seed limitation: `prisma/seed.ts` is not a faithful mirror of the in-memory seed. It creates listings (the in-memory seed creates none, which is why the E2E spec asserts the listings empty state), omits the org member user, and uses the placeholder string `REPLACE_WITH_HASHED_PASSWORD_IN_REAL_SEED` as every password hash, so seeded users could not log in through the Prisma path. No seed runner is configured in any `package.json`, so `npx prisma db seed` has no command to run. The seed needs bcrypt hashed dev passwords and a configured runner before the Prisma path can be demoed. The README no longer instructs running it.
- Prisma schema gaps the adapter documents in code: `Donation` has no column for the domain audit `history` (recoverable from the outbox stream; a follow-up migration should add it), and `Notification` has no `donationId` column (the link lives in the outbox payload). The Prisma adapter returns empty history and empty `donationId` on reads.
- The API loads the app-services ESM build via Node 22 `require(esm)`; engines and CI are pinned to Node 22 accordingly.
- No deployment. No hosted demo. The web app runs locally only.
